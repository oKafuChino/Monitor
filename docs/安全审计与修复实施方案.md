本次只新增报告，不修改业务代码、数据库、部署配置或依赖。结论来自当前源码、路由及调用链检查；文中“确认”指代码缺陷及可达路径已确认，不代表已经在真实部署上完成攻击复现。

## 1. 审计结论

当前版本需要优先补强主站的输入限制、Agent 字段权限、双重验证边界及长连接撤销。最值得先修复的四项问题是：

1. 匿名请求在鉴权前就可能被完整读入内存；部分解压、WebSocket 和查询操作也缺少资源上限。
2. 持有某节点 Agent token 的调用者，可以通过基础信息上报修改该节点的隐藏状态、token 等管理字段。
3. 已登录会话可以绕过现有双重验证保护，直接替换已启用的 2FA；数据库管理、API key 设置和备份等路径也没有形成一致的二次验证边界。
4. WebSocket 只在握手时取得身份；撤销会话或轮换凭证后，旧连接仍可能保留权限，旧实时接口还缓存节点隐藏状态。

分享功能的独立路由、独立前端、随机凭证、哈希存储和逐请求有效性验证已经落实，本次没有确认“仅凭分享链接访问主站管理接口”的路径。但独立端口不等于独立进程或独立资源：主站发生内存耗尽，分享站也会受影响。独立域名也不能保证真实主站地址无法被发现，最终仍要靠网络访问控制保护主站。

### SEC-01：输入与计算资源没有统一上限

证据：

- [Auth.go:142](E:/Github/Monitor/web/api/Auth.go:142)：`extractClientToken` 在非 GET 请求中无上限 `io.ReadAll`，解析 JSON 再恢复 Body。
- [principal.go:18](E:/Github/Monitor/web/api/principal.go:18)：匿名、无有效管理员凭证的请求会走上述逻辑；它位于路由处理和路由局部大小限制之前。
- [report_v2.go:23](E:/Github/Monitor/web/api/client/report_v2.go:23)：gzip 解压输出及普通上报体无上限读取。
- [transport.go:89](E:/Github/Monitor/web/rpc/jsonrpc/transport.go:89)、[safe_conn.go:38](E:/Github/Monitor/web/connection/safe_conn.go:38)：整条 WS 消息读入内存；主 RPC 的 POST 和批量条目也没有完整限制。
- [runtime.go:117](E:/Github/Monitor/internal/server/runtime.go:117)、[guide_server.go:59](E:/Github/Monitor/internal/server/guide_server.go:59)：主站/向导的 `http.Server` 未设置读取头、空闲等超时；分享监听已有相应配置。
- [public.metric.go:152](E:/Github/Monitor/web/rpc/jsonrpc/public.metric.go:152)、[public.metric.go:716](E:/Github/Monitor/web/rpc/jsonrpc/public.metric.go:716)：指标数、实体数、时间范围及 `max_points` 没有统一硬上限，后者仅要求大于零；部分数据先全量查询，再在内存组织结果。

影响：即使业务接口最终返回 401/404，也可能已经分配大量内存。有效 Agent 还能通过高压缩比数据或过大 WS 消息放大消耗。开放主站的匿名指标查询能够增加数据库和内存负担；开启私有站点可限制指标访问，但不能修复鉴权前读 Body。实际耗尽阈值取决于机器资源和代理限额，本次未做压力实验。

修复要求：

1. 在身份中间件之前安装路由感知的体积限制；取消全局 JSON Body 扫描取 token。凭证从明确的 header 读取，兼容期只在 Agent 路由接受旧 query token。
2. 同时限制压缩输入与解压输出。输出用 `LimitReader(limit+1)` 等方式检测超限，不能先 `ReadAll` 后检查长度。
3. WS 限制帧/消息体积，同时限制解压后的消息长度；不能假定 gorilla 的 `SetReadLimit` 单独覆盖解压输出。超限用 1009 关闭，并添加写超时及存活检查。
4. JSON-RPC 限制批量条目、嵌套/集合尺寸、每连接频率及全局并发；查询设可取消 deadline，WS 不继续以无截止时间的 `context.Background()` 执行数据库工作。
5. 查询预算包含指标数、实体数、时间范围、序列总数、总点数和最终响应字节数；存储层必须尽早限制扫描/物化。仅限制最终图表点数不够。
6. 可从普通 JSON 1 MiB、登录 16 KiB、RPC batch 20 条、查询超时 10 秒开始测量；UI 设置、favicon 和备份分片使用各自现有合理限额，不能统一降为 1 MiB。主站历史跨度上限应结合已有保留期和 UI 功能配置，不能直接照搬分享的 30 天而破坏现有历史查询。
7. 设置 `ReadHeaderTimeout`、`IdleTimeout`；正文读取、长轮询和上传分别管理超时。Agent 最长约 25 秒拉取及客户端 35 秒超时需要保留兼容窗口。对上报数组、字符串及每节点速率加上限，避免高基数 GPU 等数据拖垮共享存储。

验收：用小限额的本地测试模拟超限输入，不发送实际超大文件；覆盖匿名 404/401 路径、无 Content-Length、gzip、WS 压缩、超大 batch/数组、查询取消、正常备份分片与 Agent 长轮询。断言限制在业务执行和大分配前生效。

### SEC-02：Agent 可以修改自己节点的管理员字段

调用链：`agent.basicInfo` → `ingestBasicInfo` → `saveClientBasicInfo` → `clients.SaveClientInfo` → GORM `Updates(map)`。

证据：[report_v2.go:64](E:/Github/Monitor/web/api/client/report_v2.go:64)、[uploadBasicInfo.go:23](E:/Github/Monitor/web/api/client/uploadBasicInfo.go:23)、[client.go:30](E:/Github/Monitor/database/clients/client.go:30)、[client.go:267](E:/Github/Monitor/database/clients/client.go:267)、[Client 模型](E:/Github/Monitor/database/models/models.go:11)。当前只验证部分硬件数字，并没有字段白名单。

持有节点 A token 的调用者可以在 `params.info` 添加 `hidden:false`、`token`、`public_remark`、`price`、`group` 等字段，改变本应由管理员控制的节点状态。服务器覆盖了 UUID，所以确认的范围是自己的节点，不能宣称可直接修改其他节点。隐藏状态被解除会破坏站点隐私约束；原已撤销分享不会因此自动恢复。

修复要求：

- 为 Agent 定义独立 DTO 和明确更新字段白名单，数据库层也限制可写列；管理员编辑使用另一套 DTO，禁止直接复用任意 map。
- Agent 仅写 CPU、系统、内存、磁盘、网络地址等确有需要的机器属性；`name`、`hidden`、`token`、备注、分组、价格、账单、排序、流量限额、创建时间均不允许上报覆盖。
- `uuid` 永远从认证主体取值；字符串、数值和集合有长度/范围约束，未知管理字段拒绝且不产生部分写入。
- 列白名单应使用规范的协议字段，避免通过 Go 字段名、数据库列名、大小写或别名绕过。

验收：HTTP/WS 各创建 A、B 两节点。A 提交管理字段全部失败且 DB 不变；伪造 B UUID 无效；合法完整/部分硬件上报仍成功；隐藏及分享撤销事务不退化。

### SEC-03：双重验证保护可被现有管理员会话绕过

直接路径：[router.go:101](E:/Github/Monitor/web/router/router.go:101) 仅给 disable 挂了二次验证；[2fa.go:24](E:/Github/Monitor/web/api/admin/2fa.go:24) 的 enable 校验新 secret 的新验证码后，调用 [accounts/2fa.go:30](E:/Github/Monitor/database/accounts/2fa.go:30) 无条件覆盖旧 secret。

因此，拿到会话但不知道原 TOTP 的调用者，能够重新 generate，再 enable 自己的新 secret。`2fa_secret` 还直接保存在 `Secure=false` 的客户端 Cookie 中，未绑定到服务端一次性设置流程。

只给 enable 添加校验仍不完整：

- [admin.dbquery.go:64](E:/Github/Monitor/web/rpc/jsonrpc/admin.dbquery.go:64) 的 DB 查询/执行仅要求管理员身份，可读取或更改用户 2FA 等数据库内容。
- [admin.misc.go:119](E:/Github/Monitor/web/rpc/jsonrpc/admin.misc.go:119) 的设置接口可以读取配置，写入接口可以更换 API key；[AuthSensitive.go:29](E:/Github/Monitor/web/api/AuthSensitive.go:29) 明确让 API key 绕过 TOTP。
- 备份下载/导入只要求管理员角色；备份包含可离线读取的认证数据。
- 当前 RPC 敏感登记只有 `admin:getAgentStartupConfig`，无法形成凭证操作的一致保护。

这不是匿名鉴权绕过，前提是已取得管理员会话；问题在于原本希望依靠二次验证拦截的会话窃取场景仍可得手。原生 SQL 是保留的管理功能，不应误报为 SQL 注入。

修复要求：

1. 已启用 2FA 时，再次 enable 应拒绝，改用明确的 change 流程：验证旧因子，再验证新因子，原子提交。首次启用同样要求近期重新认证。
2. pending secret 留在服务端短期存储，绑定用户、当前 session、用途和过期时间；浏览器只持随机操作标识。完成/取消即失效，不接受任意 secret Cookie。
3. 制定集中敏感操作表：原生 SQL 的读/写、完整备份导出与恢复提交、API key 创建/读取/轮换、认证设置、OAuth 绑定/解绑、2FA 更改、凭证导出都纳入。REST、RPC POST、RPC WS 必须一致执行。
4. 普通设置响应默认脱敏；保留单独的受保护“显示凭证”操作。普通 session 列表使用不可认证的 session ID 和掩码，不返回所有可复用的裸 session token。
5. 明确定义 API key 权限：现有 key 可继续作为显式高权限自动化凭证，但普通会话不能免二次验证读取/重置它再借其提权。后续可支持 key scope，默认不给新 key 认证设置/完整数据库导出能力。
6. 无 2FA 的账号对高风险操作要求近期密码/OAuth 重新认证；修改密码、2FA、外部绑定后按策略撤销其他会话，与 SEC-04 联动。
7. 前端账号、设置、数据库和备份页面增加统一二次验证流程；不把 TOTP 放 URL query，也不持久化验证码或新 secret。

验收：只有有效 session、没有旧因子时，重新 enable、DB 读写认证表、获取/重置 API key、备份导出/恢复、OAuth 绑定全部不能绕过。正当用户完成重新认证后可以继续使用这些保留功能。不得以删掉数据库/备份功能代替修复。

### SEC-04：WebSocket 身份和可见性是握手时的快照

证据：[transport.go:97](E:/Github/Monitor/web/rpc/jsonrpc/transport.go:97) 在循环外创建 `meta`；[sessions.go:71](E:/Github/Monitor/database/accounts/sessions.go:71) 撤销仅删除 DB 记录；[ws.go:32](E:/Github/Monitor/web/api/ws.go:32) 在循环外计算 `isLogin` 和 `hiddenMap`。

管理员 RPC 连接可能在 logout、删除会话、过期或密码修改后继续调用管理员方法。旧 `/api/clients` 的匿名连接会在节点后来隐藏后继续收到其数据，新隐藏节点也不在原快照中。Agent WS 同样只在建立连接时识别 UUID，轮换 token 不会让该连接重新验证。节点删除虽然调用 `DeleteConnectedClients` 清理 map，但 [connections.go:78](E:/Github/Monitor/web/agent/connections.go:78) 明确不关闭底层连接，原读取循环仍可能接收上报并重建运行时状态；删除也必须覆盖真实连接失效。

此外，[accounts.go:35](E:/Github/Monitor/database/accounts/accounts.go:35) 的 CLI 强制重置密码没有撤销会话；`GetUserBySession` 自身不校验过期，应统一走有效会话查询，避免新增调用路径再次遗漏。

修复要求：

- 每条特权 WS 消息重新确认 session/API key/Agent token 有效；个人规模优先选择简单可靠的数据库验证，若使用缓存需有明确失效机制。
- 撤销事件主动关闭相应连接；每消息校验作为兜底。到期定时关闭，禁止只靠用户重新连接。
- 每次返回实时数据都依据当前可见节点集合过滤，数据库查询失败时拒绝返回，不用过时缓存继续放行。
- 连接注册/关闭与 Agent 重连使用连接 ID 比较，避免旧连接的清理误删新连接；所有事件推送也检查接收端授权。
- CLI 密码重置、网页登录改密、2FA 更改、API key/token 轮换遵循统一撤销规则。通用 SQL 修改认证状态应触发广义失效或由每消息验证兜底。

验收：建立连接后逐项执行注销、到期、删会话、改密、CLI 重置、轮换 key/token、隐藏节点、切换私有站点。下一条请求不能继续使用旧权限；匿名旧连接不能读刚隐藏节点。正常重连、心跳、Ping 和 I/O 上报保持可用。

### SEC-05：首次部署可能被抢先初始化

证据：[install.go:64](E:/Github/Monitor/web/install/install.go:64) 的 complete 和备份上传仅检查控制器 active；[guides.go:54](E:/Github/Monitor/internal/server/guides.go:54) 初装不挂身份认证；[compose.yaml:6](E:/Github/Monitor/compose.yaml:6) 默认发布主端口到所有主机接口。

已有管理员的正常运行实例不受这条路径影响。风险发生在新部署、数据丢失后重新初始化、或恢复失败进入无用户状态时：先访问者可建立管理员账户或导入自己的备份。仅“没有用户”不是部署者身份的证明。

修复要求：首次启动生成至少 32 字节随机一次性 setup token，仅通过本地控制台或受限文件交给部署者；安装 API 的创建与上传操作必须校验 token，并绑定一次设置流程。不要把 token 放 URL、网页源码或一般日志。完成立即作废，默认关闭再次初始化；代理 Origin/CSRF 校验不能替代部署者认证。安装文档提供 loopback + SSH 转发/VPN 初始化方式。

验收：新实例无 token/错 token 的 complete、upload init/chunk/merge/cancel 均拒绝；有效 token 能完成一次安装；完成、重启后不能复用。恢复失败不能自动暴露无认证的安装入口。

### SEC-06：QQ OAuth 的 state 未绑定到授权结果

证据：[oauth.go:40](E:/Github/Monitor/web/api/public/oauth.go:40) 跳过 QQ 的 query state 比较；[qq.go:25](E:/Github/Monitor/web/oauth/qq/qq.go:25) 生成 state 但请求聚合平台时没有建立可验证的回传绑定；[qq.go:75](E:/Github/Monitor/web/oauth/qq/qq.go:75) 只检查 Cookie state 存在于缓存。

这只能证明浏览器曾发起某次流程，不能证明回调 code 属于同一流程。攻击者自己的 code 可能被受害者流程接受，形成登录 CSRF 或外部账号错误绑定。利用受聚合平台 code 约束、浏览器 Cookie 及受害者操作时机影响；本次未连接真实 QQ 平台做端到端复现，不能宣称可无条件接管任意账号。

修复要求：取消提供商跳过逻辑。使用聚合平台确实支持的 state 回传，或者被平台原样保留、绑定本次 code 流程的一次性回调 nonce。nonce 必须同时绑定浏览器会话、提供商、用户及 login/bind 用途，原子消费，不能用“任意有效 Cookie state”替代。平台不支持可靠绑定时，应禁用该不安全适配并明确报错，不默默放宽校验。

绑定/解绑改为经近期重新认证的操作，GET 导航不直接启动账号绑定。回调再次检查 OAuth 开关及提供商是否仍匹配。所有 OAuth Cookie 采用可靠的 HTTPS 判断、HttpOnly、合适的 SameSite；外部 HTTP 客户端设置超时和响应大小限制，错误响应不透出原始 token/完整上游正文。

验收：错/缺 state、A 浏览器 code + B 浏览器 state、重放、并发回调、过期、登录 code 用于绑定、流程中关闭 OAuth 或切换 provider 全部拒绝；正常支持的 provider 登录绑定仍成功。

### SEC-07：密码存储不适合抵抗离线破解

证据：[accounts.go:15](E:/Github/Monitor/database/accounts/accounts.go:15)、[accounts.go:48](E:/Github/Monitor/database/accounts/accounts.go:48)。目前使用公开固定盐加一次 SHA-256；这不是明文存储，但攻击者取得 DB/备份后可高速离线试密码。

修复要求：选择 Argon2id，使用独立随机盐和带版本/参数的存储格式；针对低配主机测量内存与耗时，例如从 19 MiB、2 次迭代、并行度 1 开始，结合登录并发限制调整。也可选择经过评估的 bcrypt，但必须处理其输入长度约束。

兼容旧记录：成功验证旧密码后以同一明文重新哈希并写回；新建、网页登录改密和 CLI 重置立即使用新格式。不能对旧 hash 再 hash 来替代迁移，也不能误把旧记录全部判为无效。限制密码输入最大长度及散列参数解析范围，比较使用库的安全校验方法。

验收：旧用户可登录并升级，新用户/改密/CLI 重置采用新格式；同密码两用户盐/hash 不同；错误、畸形和超大输入安全失败；迁移并发和恢复旧备份可用。记录旧二进制不能验证新格式的回滚限制。

### SEC-08：没有主站登录/验证码限速

证据：[login.go:37](E:/Github/Monitor/web/api/public/login.go:37)、[accounts/2fa.go:35](E:/Github/Monitor/database/accounts/2fa.go:35)。本次搜索未找到主站登录或敏感 TOTP 的尝试限速；已有 limiter 仅服务分享站。

修复要求：密码登录按规范化账号 + 可信客户端 IP + 全局并发设置组合预算，TOTP 使用独立预算及短期冷却，不因换 IP 或换 session 完全清零。使用有过期及容量上限的计数结构；不能靠永久锁账号阻止攻击，否则攻击者可把个人管理员锁在门外。统一外部失败文案，记录脱敏失败事件。若要求 TOTP 防重放，使用原子消费/短期授权操作票据，避免同一合法页面多个请求互相冲突。

主站默认代理信任、`GetScheme` 直接信任转发头的问题需要同时梳理：只接受配置的可信代理；Origin 校验比较完整 scheme/host/有效端口，不能仅比较 host。为基于 Cookie 的写操作建立明确的 CSRF/Origin 策略；CLI/Agent 的 header token 路径单独处理。

验收：同账号换 IP、同 IP 换账号、错误 TOTP、并发登录、伪造 X-Forwarded-For、冷却恢复均有覆盖；新散列上线后仍不能被大量并发登录耗尽内存。

### SEC-09：Agent token 在传输周边暴露

证据：[basicInfo.go:71](E:/Github/Monitor/komari-agent/server/basicInfo.go:71)、[websocket.go:134](E:/Github/Monitor/komari-agent/server/websocket.go:134)、[websocket.go:217](E:/Github/Monitor/komari-agent/server/websocket.go:217)：凭证拼在 `?token=`。HTTP 错误对象可能包含完整 URL，反代也常记录 query。安装脚本 [install.sh:632](E:/Github/Monitor/komari-agent/install.sh:632) 将参数写入服务 ExecStart，系统级服务文件没有专门限制凭证可读性；运行参数也可能被本地进程列表看到。

主站自己的 GinLogger 已省略 query，不应误报为它正在直接记录 query token。风险在 Agent 错误、代理、服务配置和进程参数。

修复要求：

- 服务器先支持 Agent 专用 `Authorization: Bearer` 或明确的专用 header，再升级 Go Agent 的 HTTP 和 WS 握手。注意当前服务端 `extractClientToken` 没有完成 Agent bearer 识别，不能只改客户端。
- 服务端按路由和凭证类型分辨管理员 key 与 Agent token，不扩大 Agent 权限；兼容 query 的范围限 Agent 路由并设迁移期。
- Agent 以受限配置文件读取 token，Linux 文件 0600、目录 0700/0750，并匹配服务运行用户；Windows 设置等效 ACL。不能只隐藏前端安装命令。
- 网络错误采用脱敏结构化记录；重定向禁止降级到 HTTP，敏感 header 不转发到未授权目标。
- 若既有日志/配置曾向不可信主体开放，升级后轮换相关 token；否则无需无差别轮换全部凭证。

验收：强制 DNS、连接和 HTTP 错误时日志没有 token；URL 不含凭证；旧/新 Agent 在过渡期都可上报；进程参数不含 token；低权限本地账户不能读取凭证文件。

### SEC-10：不安全 TLS 选项扩展到了 Agent 更新下载

证据：[update.go:114](E:/Github/Monitor/komari-agent/update/update.go:114) 更新客户端复用 DNS HTTP client；[resolver.go:209](E:/Github/Monitor/komari-agent/dnsresolver/resolver.go:209) 由全局 `IgnoreUnsafeCert` 控制证书验证。更新 digest 来自同一 API 流程；[update.go:470](E:/Github/Monitor/komari-agent/update/update.go:470) 在 digest 缺失时仅警告并放行。

默认安全 TLS 配置不等于存在此漏洞触发条件。但若用户为连接自签名探针开启该开关，更新链也失去服务端身份校验。网络中间人可同时伪造发布元信息、摘要和二进制，使校验失去意义；影响可达 Agent 运行用户权限，常见 root 部署尤其严重。

修复要求：更新使用独立、始终校验证书的 HTTP client，不继承主站连接的跳过验证选项；仅允许可信 HTTPS 下载与重定向目标。主站自签名场景提供 CA/证书 pin 配置。摘要缺失默认拒绝；如果必须兼容老 release，只提供明确的本地人工选项，不能让网络响应自行降级。可进一步引入独立公钥签名，但不能以“摘要匹配”宣称已经验证发布者身份。

验收：即使上报配置开启 IgnoreUnsafeCert，更新仍拒绝自签名/错误域名/过期证书；缺 digest、摘要不符、降级重定向、超大文件拒绝且不替换原二进制；正常 GitHub 更新和切换版本成功。

### SEC-11：分享会话名额耗尽

证据：[service.go:120](E:/Github/Monitor/internal/sharing/service.go:120)、[server.go:51](E:/Github/Monitor/web/share/server.go:51)。每次 `/s/:token` 都创建新会话，不复用同浏览器有效会话；每链接最多 100 条，有效期最长 24 小时。达到上限后新访客无法进入。

有效链接持有者可以在现有速率限制内反复进入并占满名额；普通重复打开和链接预览也会消耗名额。这是可用性问题，不能用来跨节点读取数据；现有会话不一定立即受影响。

修复要求：先复用同浏览器、同链接且仍有效的会话，复用必须再次校验链接、节点、撤销和到期；避免续期无限延长链接有效期。对新会话设置更严格预算，名额满时采取明确的恢复策略，例如受限 LRU 替换并告知被替换会话重新进入，或管理员重置会话；配合创建速率限制，避免替换本身成为大规模踢人手段。必要时由用户交互确认换票，降低链接预览消耗。禁止为了修复名额问题取消撤销校验。

验收：同浏览器多次打开只占一个名额；无 Cookie 换票受限；满额后有可恢复路径；过期、撤销、隐藏、删除及 1d/1w/1mo/forever 的既有语义保持不变。多标签打开不同节点的单 Cookie 覆盖问题应同时明确产品行为，避免展示内容与用户预期不一致。

### SEC-12：备份恢复失败可能破坏当前数据

证据：[restore.go:112](E:/Github/Monitor/web/backup/restore.go:112) 上传验证检查标记、声明展开尺寸及条目数，未完整读取所有条目验证 CRC/路径/数据库；[dbcore.go:345](E:/Github/Monitor/database/dbcore/dbcore.go:345) 先备份后删除数据，再解压，错误主要记日志后继续，预备份失败也没有可靠中止。

[unzipToDir:120](E:/Github/Monitor/database/dbcore/dbcore.go:120) 已有目录边界检查，因此本次不认定简单 `../` ZIP 条目可以任意写到 data 外。实际问题是：路径错误、损坏条目或无效数据库可能到清理原数据之后才被发现，且仍移除待恢复文件。配合无部署者认证的初装流程还会放大影响。

修复要求：在独立临时目录流式解压并实际计数，拒绝越界、绝对路径、软链接/特殊文件、重复路径及冲突条目，验证 CRC、必要数据库完整性和格式；限额同时覆盖元数据与实际输出字节。备份成功且预检全部通过后才执行可回滚切换；失败保留原数据、失败档案和清晰恢复状态，不继续启动到半恢复数据库。启动直接发现 backup.zip 时也必须执行同一预检。保持成功恢复后撤销全部分享的既有规则，并评估是否一并撤销管理员会话。

验收：仅在临时 data 目录测试损坏 ZIP、越界、重复条目、错误 SQLite、磁盘不足、无权写快照及切换中断；每种失败都保证原 DB 可打开且没有静默新建空库。正常完整备份恢复及外部指标数据库场景另外回归。

## 4. 次要问题与需要保留的边界

### 4.1 公开数据收敛

[publicGetPublicPingTasks](E:/Github/Monitor/web/rpc/jsonrpc/public.go:204) 返回任务完整 `Clients` 集合，可能暴露隐藏节点 UUID 和关联关系；没有返回 Ping 目标，不能扩大描述为目标地址全部泄漏。公开响应应只含当前可见节点关系。

[publicMetricEntityIDs](E:/Github/Monitor/web/rpc/jsonrpc/public.metric.go:640) 接受“不在 hidden 表中的任意请求实体”，而不只接受当前可见节点。建议改为严格可见节点白名单；对删除残留/自定义实体指标制定显式授权规则。是否已有可泄漏的残留实体数据依赖实际 DB，尚未实证。

主站 session/API key 和 Agent token 多为可复用明文存储，分享凭证已使用哈希。后续可将其他 bearer 凭证也改成哈希存储，配合仅首次展示和 ID 撤销机制；必须先梳理安装脚本、前端复制和旧节点升级兼容，不可直接删掉字段导致 Agent 全部离线。

### 4.2 前端和残留代码

检查了 `dangerouslySetInnerHTML`、Markdown 及 SVG 入口，没有确认 Agent 上报字符串直接进入可执行 HTML 的完整路径。站点自定义 HTML 属于管理员权限，不能简单算作匿名存储型 XSS。

`InlineSvgIcon` 使用手写 SVG 清洗；当前用途是后台菜单图标，不足以直接认定外部攻击者可利用。建议外部图标默认使用 `<img>`，或采用成熟 SVG 白名单清洗并禁用 SMIL 动画改属性等能力；同时限制来源。主站安全响应头/CSP 可从 Report-Only 开始，兼容图表及保留的自定义 HTML 设置，不强行移除现有功能。

Agent 的旧文件/终端代码可作为后续清理项，移除依赖和死代码能降低维护成本；本次安全修复不重新启用它们，也不把删除功能作为必要前提。

### 4.3 依赖与构建

当前没有完成可用的依赖漏洞扫描，不列未经核实的 CVE。实施时分别对根 Go module、Agent Go module 和前端锁文件扫描；根据实际版本、可达代码及运行/构建阶段区分影响。只在必要时升级依赖，不执行无评估的 `npm audit fix --force`。

检查 CI action 的固定版本、工作流最小权限和发布输入使用方式。部署镜像必须重新生成主站和分享的独立嵌入产物；源码修复但仍发布旧 bundle 不算完成。禁止把真实 token、OAuth secret、生产数据库或备份提交进测试夹具。
