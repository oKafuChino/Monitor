## 3. 部署与兼容说明

### 首次安装和主站入口

Compose 默认映射 `127.0.0.1:${MONITOR_PORT:-25774}:25774`。远程部署先使用 SSH 隧道或受控反代访问，例如在自己的电脑执行：

```sh
ssh -L 25774:127.0.0.1:25774 user@server
```

然后访问 `http://127.0.0.1:25774`。在服务器安装目录本地读取 `sudo cat data/setup-token`，在网页的部署者验证对话框输入；凭证不出现在 URL 或应用日志中。完成后文件删除；未完成安装时重启会更换凭证。API 自动化在初始化写请求中使用 `X-Setup-Token`。

需要绑定其他网卡时在 `.env` 指定 `MONITOR_BIND=明确的内网IP`。绑定 `0.0.0.0` 会开放主站网络入口，需要自行配置访问控制。分享 listener 与主站共进程，独立端口无法隔离 CPU/内存资源。

### 可信代理与重新认证

默认不信任任何代理。Compose 已把 `.env` 的 `KOMARI_TRUSTED_PROXIES` 传给容器；填写逗号分隔的实际代理 IP/CIDR，按应用看到的 TCP peer 配置，Docker 部署可能是网桥网关。代理需覆盖 `X-Forwarded-For` 和 `X-Forwarded-Proto`，保留正确 Host，不得把任意访问者列为可信代理。

启用 2FA 的敏感请求使用 `X-2FA-Code`；未启用时使用 `X-Reauth-Password`。RPC 对象参数也支持 `2fa_code`、`two_factor_code`、`otp` 或 `reauth_password`，这些认证字段在调用业务写入前剥离。验证码不再从 URL 读取。前端只为失败提示重新认证一次，凭证不写 localStorage。

浏览器 Cookie 写请求必须提供可信 Origin/Referer；关闭 CORS 显示设置不能取消该保护。CLI 自动化建议使用显式 API key；沿用 Cookie 的调用者须提供正确 Origin。API key 仍具有管理员敏感操作权限，应限制读取者和调用来源。

修改用户名/密码、绑定/解绑 SSO、启用/禁用 2FA 会撤销相关账号全部会话，需要重新登录。敏感设置和节点 token 需显式点击显示并重新认证。账号密码升级后旧二进制不能验证 Argon2id；回滚应使用支持新格式的版本或受控的旧备份。

### Agent 升级和本地凭证

先升级服务端，再升级 Agent。新 Agent 使用 `Authorization: Bearer`，服务端暂时仅在 Agent 路径兼容旧 query token；全局 JSON token 提取已删除。待全部节点升级后再安排删除 query 兼容。

Unix 安装生成 `credentials/agent.json`（0600、目录 0700，归属服务用户）；Windows 安装目录和 credentials 目录限制 SYSTEM/Administrators，自动发现文件继承受限 ACL。手动运行也应自行设置等效权限。不要同时传入 `--config` 和凭证 flags，把所有凭证放入同一配置文件。

安装命令启动时传 token 仍可能进入 shell 历史；需要避免历史凭证时，手工创建受限 JSON，安装/启动只传 `--config /受限路径/agent.json`。已写入旧服务文件或日志的 token 若曾被不可信用户读取，升级后轮换。

自签名主站可使用 `--tls-ca-file /path/panel-ca.pem`、环境变量 `AGENT_TLS_CA_FILE` 或 JSON 的 `tls_ca_file`。该配置为系统 CA 增加主站 CA，仍校验域名和有效期；保留 `ignore_unsafe_cert=false`。更新客户端独立使用系统信任链，主站自定义 CA 及跳过验证选项不会应用到更新。

### 备份恢复与失败处理

自动 ZIP 恢复目前要求主库使用默认 `./data/komari.db`，自定义路径/URI 或其他主库类型会明确拒绝。上传合并先检查目标配置，拒绝时不会安排重启；不要把 ZIP 手动放到不支持恢复的实例。外部 MySQL/PostgreSQL 指标数据库不包含在 ZIP 内，需独立备份；恢复的设置可能重新指向备份中的外部 DSN，应用后应核对连接目标。

有效 ZIP 先在 `.restore-stage` 预检，再把旧文件移到 `.restore-original`，切换完成后再启动主库/迁移并撤销会话。成功将原文件保存到 `data/backup/pre-restore-*`，失败档案保留供检查。

若启动因损坏 `data/backup.zip` 停止，先停止容器并保留完整 data 副本，再把失败 ZIP 移出待恢复位置后启动原实例。若存在 `.restore-journal.json`，先让程序处理回滚/已提交事务；不要手工删除日志和 `.restore-original`。回滚失败时按日志检查磁盘空间与权限，在恢复完原数据库及关联文件前不要强行继续启动。

不同分享节点仍共用一个浏览器 Cookie，新链接会切换当前分享会话；多标签重新请求可能要求再次进入原链接。后台“重置会话”会让既有访客重新换票，不撤销链接本身。

OAuth 提供商 HTTP 调用有 10 秒超时及 64 KiB 响应上限，不跟随 token/userinfo 请求重定向。QQ 聚合平台地址要求 HTTPS，需保持配置的登录类型并原样保留 state；HTTP 平台或依赖上游重定向的配置需先修正。

## 5. 自行实测重点及未关闭的验证项

1. 先在隔离 Linux 环境编译根模块和 Agent 模块；运行审计报告第 6 节的回归、race、漏洞扫描及前端/归档验收命令。现有测试夹具可能需要按新的安装 token、Origin、密码格式和有效 SQLite 预检规则更新，不能取消保护来适配旧夹具。
2. 优先检查匿名超限、Agent 管理字段越权、启用后的 2FA 替换、敏感 SQL/备份/凭证获取，以及轮换/撤销后的旧 WS。连接定期检查间隔约 1 秒，已经通过授权并开始执行的操作不能假设会被回溯撤销；并发隐藏/删除/轮换边界需 race 与行为测试。
3. 使用小体积本地输入验证 gzip、WS 压缩、批量 RPC、历史预算及上传。确认正常 5 MiB 分片、Agent 25 秒长拉取、I/O 真零/缺失、Ping 和版本切换保持兼容；大规模节点可能需要在受控实测后调整初始限额。
4. OAuth 使用模拟提供商检查错配、重放、到期、用途与配置切换，再检查实际 QQ 聚合平台 state 回传及其他提供商流程。更新检查证书、缺 digest、错误 digest、HTTP/跨主机重定向拒绝，确认正常 release 的 digest 可用。
5. 仅在临时 data 副本中演练损坏 ZIP、路径冲突、错误 SQLite、磁盘不足、权限错误、切换/回滚/提交中断。当前事务写入文件日志并 Sync，但未验证真实断电及不同文件系统的目录持久化行为。
6. 检查 Linux 各 init 系统与 Windows NSSM 的参数、权限和自动发现；检查主/分享双 origin、Cookie、HTTPS 代理、端口访问控制及全链路日志脱敏；最后执行真实节点升级及连续 I/O 采样。

后续增强不作为本次已完成内容：其他 bearer 凭证的哈希存储及 scope、独立发布公钥签名、CSP Report-Only/成熟 SVG 清洗、旧 Agent 不可达代码清理、依赖/CI 权限专项扫描。TOTP 当前按用户限速，未新增跨操作验证码一次消费机制。
